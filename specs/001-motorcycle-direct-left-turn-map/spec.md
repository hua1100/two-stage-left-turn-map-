**狀態**: 草稿
**輸入**: 使用者描述：「我要做可以在地圖上顯示機車不用兩段式左轉路段的工具，最好可以在 google map、apple map、OpenStreetMap、organicmaps 這些手機 app 上使用」

## 專案背景

在台灣，機車在三車道以上道路的路口原則上需要進行「兩段式左轉」，但台北市政府針對部分路口開放機車可以直接左轉。目前共有 121 個路口開放此項例外措施（資料截至民國 114 年 4 月）。

機車騎士在不熟悉的路段行駛時，往往不清楚哪些路口可以直接左轉，導致：
- 誤以為需要兩段式左轉而繞遠路
- 或誤以為可以直接左轉而違規

本專案旨在建立一個工具，將這些開放直接左轉的路口資訊整合到常用的地圖應用程式中，讓機車騎士能即時查看。

## 使用者情境與測試 *（必填）*

### 使用者故事 1 - 匯出 Google Maps/Apple Maps 相容格式 (優先級：P1)

身為一位機車騎士，我希望能在我常用的 Google Maps 或 Apple Maps 上看到可以直接左轉的路口標記，這樣我在導航時就能知道哪些路口不需要兩段式左轉，節省時間並避免繞路。

**此優先級的原因**: Google Maps 和 Apple Maps 是台灣使用率最高的導航 app，涵蓋最大量的使用者群。提供這兩個平台的支援能讓最多騎士受益。

**獨立測試**: 可透過匯出 KML/KMZ 檔案，在 Google Maps 或 Apple Maps 中匯入，驗證所有 121 個路口都正確顯示標記與資訊。

**驗收情境**:

1. **Given** 使用者已下載匯出的 KML 檔案，**When** 在 Google Maps 中匯入該檔案，**Then** 地圖上應顯示 121 個路口的標記點
2. **Given** 使用者點擊地圖上的某個標記點，**When** 查看標記詳細資訊，**Then** 應顯示路口名稱、可直接左轉的方向、開放時間等資訊
3. **Given** 使用者使用 Apple Maps，**When** 開啟匯出的 KML 檔案，**Then** 地圖上應正確顯示所有路口標記
4. **Given** 使用者在台北市區導航，**When** 接近可直接左轉的路口（例如：承德路與市民大道），**Then** 應能在地圖上看到該路口的標記

---

### 使用者故事 2 - 匯出 OpenStreetMap 相容格式 (優先級：P2)

身為重視開放資料的使用者，我希望能將路口資料匯出為 GeoJSON 格式，這樣我可以在 OpenStreetMap、OrganicMaps 等開源地圖工具中使用，也方便進行資料分析和二次開發。

**此優先級的原因**: 開放資料格式支援開源生態系統，雖然使用者群較 Google/Apple Maps 小，但對技術社群和資料分析者很重要，也符合政府開放資料的精神。

**獨立測試**: 可透過匯出 GeoJSON 檔案，在 QGIS 或 geojson.io 等工具中載入，驗證資料結構正確且包含所有必要欄位。

**驗收情境**:

1. **Given** 使用者已下載匯出的 GeoJSON 檔案，**When** 在 OrganicMaps 中匯入該檔案，**Then** 地圖上應顯示所有路口標記
2. **Given** 使用者使用 QGIS 等 GIS 工具，**When** 載入 GeoJSON 檔案，**Then** 應能正確解析所有欄位（路口名稱、方向、開放時間、經緯度等）
3. **Given** 開發者想要進行資料分析，**When** 讀取 GeoJSON 檔案，**Then** 應能透過程式化方式存取所有路口的屬性資料
4. **Given** 使用者想要在 OpenStreetMap 上貢獻資料，**When** 參考 GeoJSON 中的經緯度，**Then** 應能準確找到對應路口並標記

---

### 使用者故事 3 - 建立網頁版互動地圖 (優先級：P3)

身為不熟悉匯入地圖檔案的一般使用者，我希望能直接開啟一個網頁，就能看到所有可直接左轉的路口在地圖上的分布，並能點擊查看詳細資訊，不需要額外的技術操作。

**此優先級的原因**: 提供最佳的使用者體驗和視覺化效果，但需要額外的開發和維護成本。對於能自行匯入地圖檔案的使用者，P1 和 P2 已能滿足需求。

**獨立測試**: 可透過開啟網頁，驗證地圖正確載入、所有路口標記可見、點擊功能正常、在手機瀏覽器上也能正常使用。

**驗收情境**:

1. **Given** 使用者開啟網頁版地圖，**When** 地圖載入完成，**Then** 應看到以台北市為中心的地圖，並顯示所有 121 個路口標記
2. **Given** 使用者點擊某個路口標記，**When** 彈出資訊視窗，**Then** 應顯示該路口的完整資訊（路口名稱、可左轉方向、開放時間）
3. **Given** 使用者想要搜尋特定路口，**When** 在搜尋框輸入路口名稱（例如：「承德路」），**Then** 地圖應自動縮放並聚焦到相關路口
4. **Given** 使用者在手機上使用，**When** 開啟網頁，**Then** 地圖應能響應式顯示，觸控操作順暢
5. **Given** 使用者想要分享特定路口資訊，**When** 點擊分享按鈕，**Then** 應能產生包含該路口定位的 URL 連結

### 邊界情況

- 當路口地址無法精確地理編碼（轉換為經緯度）時，系統應如何處理？
  - 建議：記錄無法編碼的路口，提供人工核對機制
- 如何處理「雙向」或「多方向」的左轉開放（例如：編號 4「南北雙向」）？
  - 建議：在標記資訊中明確列出所有允許的方向
- 當台北市政府更新路口清冊時，如何確保資料同步？
  - 建議：建立資料更新流程文件，說明如何匯入新資料並重新產生地圖檔案
- 系統如何處理重複的路口資料（例如：編號 38、39 都是「光復北路與南京東路5段」）？
  - 建議：在資料處理階段識別重複項目，合併或標註
- 未來是否考慮擴展到其他縣市？
  - 建議：採用可擴展的資料結構，預留其他縣市的欄位

## 需求 *（必填）*

### 功能需求

- **FR-001**: 系統必須能夠解析使用者提供的 HTML 表格資料，提取出 121 個路口的完整資訊（編號、分區、路口名稱、方向、開放時間）
- **FR-002**: 系統必須能夠將路口地址轉換為地理座標（經度、緯度），精確度應在 50 公尺以內
- **FR-003**: 系統必須能夠匯出 KML 格式檔案，檔案應符合 Google Maps 和 Apple Maps 的匯入規範
- **FR-004**: 系統必須能夠匯出 GeoJSON 格式檔案，檔案應符合 RFC 7946 標準
- **FR-005**: 匯出的地圖檔案中，每個路口標記必須包含以下資訊：
  - 路口名稱（例如：「承德路與市民大道」）
  - 可直接左轉的方向（例如：「北往東」）
  - 開放時間（例如：「98年以前」）
  - 所屬分區（例如：「大同」）
  - 經緯度座標
- **FR-006**: 系統必須能夠處理方向描述的多種形式：
  - 單一方向：「北往東」
  - 雙向：「南北雙向」、「東西雙向」
  - 多方向：「南往西、西往北」
- **FR-007**: 系統必須保留原始資料的編號，以便與台北市政府公告資料對照
- **FR-008**: 系統必須產生資料處理報告，列出：
  - 成功處理的路口數量
  - 地理編碼失敗的路口（如有）
  - 資料品質警告（如重複路口、格式異常等）
- **FR-009**: （選填，P3）系統必須能夠產生網頁版互動地圖，使用 Leaflet 或 Google Maps API
- **FR-010**: （選填，P3）網頁版地圖必須支援路口搜尋功能，使用者可透過路口名稱快速定位

### 非功能需求

- **NFR-001**: 資料處理過程必須可重現，任何人使用相同的輸入資料應產生相同的輸出
- **NFR-002**: 地理編碼應使用免費且可靠的服務（例如：OpenStreetMap Nominatim、Google Geocoding API 免費額度）
- **NFR-003**: 匯出的檔案大小應在合理範圍內（< 5MB），以便在手機上使用
- **NFR-004**: 系統應提供清晰的使用說明文件，包含如何在各個地圖 app 中匯入檔案的步驟
- **NFR-005**: 程式碼必須開源，採用 MIT 或 Apache 2.0 授權

### 關鍵實體 *（如功能涉及資料則包含）*

- **路口 (Intersection)**: 代表一個開放機車直接左轉的路口
  - 屬性：編號、分區、路口名稱、允許左轉方向、開放時間、經度、緯度
  - 關係：屬於某個行政分區

- **分區 (District)**: 台北市的行政分區
  - 屬性：分區名稱（例如：大同、士林、內湖等）
  - 關係：包含多個路口

- **方向 (Direction)**: 描述允許直接左轉的行駛方向
  - 屬性：起始方向、目標方向（例如：北→東、南北雙向）
  - 格式：可能是單一方向、雙向、或多個方向的組合

- **地圖圖層 (MapLayer)**: 匯出的地圖資料檔案
  - 格式：KML、KMZ、GeoJSON
  - 內容：包含所有路口的標記和資訊

## 成功標準 *（必填）*

### 可衡量結果

- **SC-001**: 系統能成功處理並匯出至少 95% 的路口資料（即 121 個路口中至少 115 個）
- **SC-002**: 匯出的 KML 檔案能在 Google Maps 和 Apple Maps 中成功匯入，且所有路口標記正確顯示
- **SC-003**: 匯出的 GeoJSON 檔案通過 GeoJSON 格式驗證器（例如：geojsonlint.com）的檢查
- **SC-004**: 地理編碼的準確度：隨機抽樣 10 個路口，人工驗證經緯度位置與實際路口的誤差應 < 50 公尺
- **SC-005**: 提供完整的使用說明文件，涵蓋至少三個平台（Google Maps、Apple Maps、OrganicMaps）的匯入步驟
- **SC-006**: 至少一位非技術背景的使用者能夠依照說明文件，成功在手機上的地圖 app 中查看路口標記
- **SC-007**: （選填，P3）網頁版地圖的載入時間應 < 3 秒（在 4G 網路環境下）
- **SC-008**: （選填，P3）網頁版地圖在主流手機瀏覽器（iOS Safari、Android Chrome）上能正常操作

## 技術方案建議

### 資料處理流程

1. **資料擷取**: 解析 HTML 表格 → 結構化資料（CSV 或 JSON）
2. **地理編碼**: 路口地址 → 經緯度座標
3. **資料驗證**: 檢查資料完整性、識別異常值
4. **格式轉換**: 結構化資料 → KML/GeoJSON
5. **品質檢查**: 驗證匯出檔案格式正確性

### 建議技術棧

- **程式語言**: Python（資料處理便利、地理編碼函式庫豐富）
- **地理編碼服務**:
  - Geopy + Nominatim（免費、開源）
  - Google Geocoding API（更準確，但有使用限制）
- **地圖資料處理**:
  - `simplekml`（產生 KML）
  - `geojson`（產生 GeoJSON）
- **網頁地圖（選填）**:
  - Leaflet.js + OpenStreetMap 圖層（開源、免費）
  - 或 Google Maps JavaScript API

### 資料結構範例

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {
        "type": "Point",
        "coordinates": [121.5168, 25.0528]
      },
      "properties": {
        "id": 1,
        "name": "承德路與市民大道",
        "district": "大同",
        "direction": "北往東",
        "opened_year": "98年以前",
        "description": "編號 1：大同區 - 承德路與市民大道（北往東）- 98年以前開放"
      }
    }
  ]
}
```

## 風險與限制

1. **地理編碼準確度**: 部分路口名稱可能過於簡略或有歧義，導致地理編碼不準確
   - 緩解措施：人工審查失敗案例、提供手動校正機制

2. **資料時效性**: 台北市政府可能隨時更新路口清冊
   - 緩解措施：在文件中註明資料日期、建立更新流程

3. **平台相容性**: 不同地圖平台對 KML/GeoJSON 的支援程度可能不同
   - 緩解措施：在主要平台上實際測試匯入功能

4. **授權問題**: 確保使用的地圖服務和資料符合授權條款
   - 緩解措施：使用開放授權的資料和工具、在文件中說明授權
